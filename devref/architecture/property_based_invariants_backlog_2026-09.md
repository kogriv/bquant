## 1. Что уже есть и чего нет

**Есть — правила.** Инварианты вшиты в модели и проверяются конструктором:

* `ZoneInfo` (G66): `start_idx <= end_idx`, `duration == end - start + 1`,
  `start_time <= end_time`, `len(data) ∈ {0, duration}`;
* `SwingContext` (G66, G70): `indices` отсортированы и совпадают с точками по индексу,
  причина пустоты (`degraded`) — только у пустого контекста;
* контракт входа (G72): ось времени неубывающая и уникальная, в цене нет дыр.

**Есть — примеры.** Тесты кормят эти правила данными, которые придумал человек:
встроенные сэмплы, синтетические кадры на 12/40/300/400 баров, восемь «странных» входов
G72.

**Нет — того, кто ломает правила нарочно.** Ни один тест не генерирует входы сам.
Значит покрыт ровно тот набор форм, который пришёл в голову автору теста; G72 — прямое
доказательство, что этого набора мало: три из восьми придуманных входов дали дефекты,
и придуманы они были только потому, что кто-то сел и стал придумывать.

## 2. Объём — узкий и названный

**Входит:**

* генератор OHLCV-кадров: длина, наличие дыр во времени, повторы, плоские участки,
  скачки, разные таймзоны, разные таймфреймы;
* проверка на сгенерированных входах правил из §1 — то есть тех, которые **уже** объявлены
  в моделях, а не новых;
* флагманский путь `analyze_zones → build()`: каждая построенная зона удовлетворяет своим
  инвариантам; свинги зоны лежат внутри её баров; сумма длительностей зон не превосходит
  числа баров; зоны не перекрываются;
* уменьшение найденного контрпримера до минимального (это даёт библиотека).

**Не входит:**

* «свойства» бизнес-смысла (стационарность, качество метрик) — это исследование, не тест;
* расширение на CLI, визуализацию и весь публичный API — отдельная работа, если понадобится;
* замена существующих тестов. Генератор **добавляется** к ним, а не вместо: пример с
  понятным числом читается человеком, генератор ищет то, чего человек не придумал.

## 3. Критерий готовности

1. Правила из §1 проверяются на **сгенерированных** входах, а не только на придуманных.
2. Найденный контрпример печатается минимальным и воспроизводится фиксированным seed —
   иначе красный тест невозможно разобрать.
3. Прогон укладывается в бюджет сьюта: генератор идёт по умолчанию с небольшим числом
   примеров, глубокий прогон — отдельной меткой (как `slow`), чтобы релизный гейт мог
   позвать его целиком, а обычный прогон не удлинялся вдвое.
4. Мутация: снять любой инвариант из §1 — генератор обязан покраснеть, и красным должен
   быть **минимальный** пример, а не случайный.
5. Если генератор за разумное число примеров ничего не находит — это тоже результат, и он
   записывается: «правила выдержали N сгенерированных форм», а не «тест зелёный».

## 4. Цена и риски

**Цена:** полдня-день. Библиотека (`hypothesis`) — новая зависимость **только для
разработки** (`dev`-extra), в рантайм пакета не входит.

**Риск первый — недетерминированность.** Тест, который падает раз в двадцать прогонов на
разном входе, хуже отсутствующего: его начинают перезапускать. Снимается фиксированным
seed по умолчанию и отдельной меткой для широкого поиска.

**Риск второй — генератор без смысла.** Случайные числа в колонках `open/high/low/close`
дают кадры, которых не бывает (`low > high`), и тест начнёт ловить не дефекты, а
собственный генератор. Генератор обязан строить **допустимые** OHLCV, а недопустимые —
только там, где проверяется отказ.

**Риск третий — подмена предмета.** Генератор проверяет правила, которые уже объявлены.
Если по ходу захочется «заодно» объявить новые — это отдельная правка с замером, а не
строка в этом бэклоге.
