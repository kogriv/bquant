# G39 — Валидация отвечала «модель устойчива», не измерив ничего

**Заведён и исправлен:** 2026-08-31, волна 3 прохода по докам (`api/analysis/statistical.md`).
**Статус:** ✅ исправлен.

---

## 1. Как нашли

Прогоном примеров страницы. Из 21 блока четыре падали, и один — `out_of_sample_test` —
с `KeyError: 'total_zones'`. Соседний блок (`walk_forward_test`) при этом **не падал**, а
печатал `0.0 0.0`. Разница в поведении на одних и тех же данных и была зацепкой: там, где
один путь спотыкался, другой отвечал нулями.

## 2. Механизм

`ValidationSuite._extract_metrics` разбирал результат анализа так:

```python
if isinstance(analysis_result, dict):        return analysis_result
elif hasattr(analysis_result, 'to_dict'):    return analysis_result.to_dict()
elif hasattr(analysis_result, 'results'):    return analysis_result.results
```

`AnalysisResult` — собственный тип пакета — имеет **и то, и другое**. Побеждала ветка
`to_dict()`, а она кладёт метрики на уровень глубже:

```
{'analysis_type': ..., 'timestamp': ..., 'data_size': ..., 'results': {метрики}, 'metadata': ...}
```

Дальше по файлу **девять раз** стояло `metrics.get(metric_key, 0)`. Метрика не находилась
никогда, подставлялся ноль, ноль сравнивался с нулём:

```
degradation_pct = 0.0
success         = True          ← «деградации нет, модель устойчива»
```

Замер на 400 барах, метрика `total_zones` (28 на обучении, 12 на тесте):

| | было | стало |
|---|---|---|
| `train_metrics['total_zones']` | отсутствует | 28.0 |
| `test_metrics['total_zones']` | отсутствует | 12.0 |
| `degradation_pct` | **0.0** | **57.1** |
| `success` | **True** | **False** |

То есть модуль сообщал «держится» там, где падение метрики больше половины.

## 3. Почему это худший случай сегодняшней формы

За день это пятый ноль-как-измерение (G34, G35, G37, G38 и этот), но остальные портили
метрику. Здесь — **вердикт**. Модуль существует ровно затем, чтобы ответить, держится ли
модель вне обучающей выборки; ответ «0% деградации» неотличим от «не измерено», и именно
он выдавался.

## 4. Почему не поймал сьют

`tests/unit/test_validation_suite.py` — 26 проверок, все передают `analyze_func`,
возвращающий обычный `dict`. С `dict` первая ветка срабатывает верно, и дефекта нет.
Тип, на котором ломается, — **собственный тип пакета**, и его в проверках не было ни разу.

Показательнее другое: `test_all_validation_methods` вызывал `sensitivity_analysis` с
функцией, возвращающей ключ `metric`, при умолчании `metric_key='total_zones'` — и
проходил. Проверял он только `isinstance(...)`, а числа под ним были нулями от
несовпадения ключей. Проверка зеленела на пустоте.

## 5. Починка

- **Порядок ветвей в `_extract_metrics`:** `results` раньше `to_dict()`, с объяснением,
  почему порядок существен.
- **`_metric(metrics, key, where)`** вместо девяти `.get(key, 0)`: отсутствие метрики —
  `AnalysisError`, называющий и запрошенный ключ, и список доступных. Нечисловое
  значение — тоже отказ: сравнивать между окнами можно только число.
- `test_all_validation_methods` в существующем сьюте назвал свою метрику явно и получил
  проверку на непустой результат.

**Проверка:** `tests/unit/test_validation_reads_the_metric_it_was_asked_for.py` — пять
утверждений, включая обратную сторону (обычный `dict` продолжает работать). Мутация: на
коде до правки краснеют 4 из 5.
